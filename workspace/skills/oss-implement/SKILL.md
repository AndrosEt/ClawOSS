# OSS Implementation — Reproduce-First Workflow

Implement a code change for a selected issue using a TDD-style reproduce-first approach.
The goal is high-quality PRs with EVIDENCE that the fix works.

## Prerequisites
- Issue selected and analyzed
- Repo cloned and analyzed by repo-analyzer skill
- Branch created with naming convention: clawoss/<type>/<issue>-<description>

## Implementation Workflow

Follow these steps IN ORDER. Do NOT skip any step.

### 1. Understand
- Read issue thoroughly — extract acceptance criteria
- Explore relevant source code
- Identify the failing behavior described in the issue

### 2. REPRODUCE (mandatory)
- Run existing tests to establish baseline (which pass, which fail)
- Find or write a FAILING test that demonstrates the bug/missing feature
- If bug report: reproduce the exact failure described
- If feature request: write a test showing the desired behavior fails
- VERIFY the test fails for the RIGHT reason (not a typo or import error)
- Record the failure output as evidence

**If you cannot reproduce the issue:**
- Check if it's environment-specific, version-specific, or already fixed
- If already fixed upstream, abandon and remove from queue
- If cannot reproduce after 10 minutes, abandon with note

### 3. IMPLEMENT
- Write the MINIMAL fix to make the failing test pass
- Do NOT over-engineer — fix only what the test requires
- Match existing code style exactly
- No "while I'm here" improvements

### 4. VERIFY (mandatory)
- Run the failing test again — it MUST now pass
- Run the FULL test suite — no regressions allowed
- If new tests fail: fix them (max 2 attempts), then abandon
- Record the passing output as evidence

### 5. REVIEW
- Self-check the diff:
  1. Is it scoped to the issue only? (no unrelated changes)
  2. Does it match repo code style?
  3. Are there any secrets, debug statements, or AI-slop?
  4. Is the change under 200 lines and 5 files?
  5. Does the commit message follow Conventional Commits?
- If 3+ checks fail, abandon

### 6. SUBMIT
- Commit with Conventional Commits format
- Create PR with:
  - Clear title referencing the issue
  - Description explaining the "why"
  - Evidence: "Before fix: [test failure output]. After fix: [test pass output]"
  - AI disclosure notice
- Push to fork, create PR

## PR Description Template

```markdown
## Summary
Fixes #<issue>: <one-line description>

## Reproduction
<describe how the bug was reproduced or what test was written>

## Before Fix
```
<test failure output>
```

## After Fix
```
<test pass output>
```

## Changes
- <bullet list of what was changed and why>

---
*This PR was generated by [ClawOSS](https://github.com/billion-token-one-task/ClawOSS), an autonomous OSS contributor. All changes were verified with automated tests.*
```

## Constraints
- Max 200 lines changed
- Max 5 files modified
- Code style must match existing codebase
- Do not introduce new dependencies unless absolutely necessary
- No AI-slop: no unnecessary comments, no over-engineered abstractions
- No helper functions used only once — inline the logic
- Variable names must match repo conventions
